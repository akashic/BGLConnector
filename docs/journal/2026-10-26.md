**Summary:** First live run of the spike against BGL staging. The deployed connector failed to connect after consent, so we troubleshot it remotely, from photos of the configuration and error screens on an IT-managed laptop, until a connection worked and *Get user details* returned 200. Along the way the harness ran T02, T03 and T05 for real. The results are recorded in the runbook, and the connector's token URLs now carry the scope. Separately, a `tools/Sync-FromUpstream.ps1` script was added for merging this repo into a copy of it.

**Discussion & decisions:**

- *Approach.* Microsoft's consent service makes the token call server-side, so the laptop couldn't see what BGL returned. The plan was to read Power Platform's error text, and to use `Get-BglToken.ps1 -TestAllStyles` on the same laptop to separate BGL-side problems from Power Platform ones. That split is what solved it.
- *What went wrong, in the order it was found.*
  1. The connector's OAuth URLs had been pasted from the BGL portal's sample URLs, so their query strings doubled up with Power Platform's own parameters.
  2. A second `pac connector create` produced a second connector with a different redirect URL.
  3. The laptop's harness had been edited to use the connector's redirect URL, which sent its codes to Microsoft's consent service.
  4. The client secret didn't match BGL's: every harness style, including BGL's documented one, got 401.

  Regenerating the secret fixed the 401s and showed that BGL wants the client credentials in a Basic header. The parameters can go in the query string or the form body.
- *The real T04 finding.* Power Platform's generic provider tries the credentials in the body first, then a Basic header, but never sends `scope` on the token call. BGL then returned 400 `invalid_scope`. Adding `?scope=smsf_partner` to the token and refresh URLs fixed it. We chose this over an APIM token proxy because it is one setting and the connection then worked end to end.
- *Recording results.* T04 was recorded as a pass only after the user confirmed *Get user details* returned 200. Open questions 1 and 2 for BGL were marked answered by testing. T05 stays undecided: BGL returned the existing token, as the earlier lesson predicted.
- *Housekeeping decisions.* The user's uncommitted `CLAUDE.md` refactor (moving harness details into `bgl-spike/harness/CLAUDE.md`) was left uncommitted. Only two line fixes were committed against the `main` version of `CLAUDE.md`. Before committing, the diff was checked for client IDs, firm IDs and email addresses, since the repo is public.
- *Sync script.* It follows a written upstream-sync procedure. It adds an `upstream` remote, makes a timestamped backup branch, stops on conflicts, handles unrelated histories with a switch, and asks before pushing. Testing on throwaway repos found that PowerShell took git's `-v` as its own `-Verbose`, so the script uses git's long options.

## Session — 12:45

**Summary:** Decided how to detect a fund going to audit. BGL's *Send to Audit* is a notification button: its only effect is the Audit webhook, and it only appears once BGL enables the app. So it can't be polled. Added hourly polling of workflow job stages as T16 (Flow C), with a *List workflow jobs* connector action. The Azure Function receiver is on hold until BGL says whether an owner app can be enabled.

**Discussion & decisions:**

- *Azure vs Power Platform.* For the webhook, an Azure Function receiver is the cleaner design. It's supported, it sees the raw bytes, it has a stable URL, the secret lives in Key Vault, and it can drop duplicates. Power Platform alone would only work through the undocumented connector proxy. The Function was started, modelled on an existing Flex Consumption Function the user pointed to, then paused when polling came up.
- *Polling.* BGL's API collection has no read endpoint for audit status (`changeAuditStatus` only writes). Workflow jobs carry `stageName`, and the system stages include *Waiting on auditor*. Polling jobs sees a stage change, not the click, so it depends on staff moving jobs. The user chose to email BGL about Send to Audit eligibility and to build the poll first.
- *Content-Type.* BGL's Send to Audit article shows the webhook sent as `application/x-www-form-urlencoded` with a JSON body. Recorded in the runbook: a receiver must verify the raw bytes whatever the `Content-Type`.
